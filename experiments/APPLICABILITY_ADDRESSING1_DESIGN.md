## 1. Вопрос (формулировка профессора)

> **Can candidate selection be made invariant to failure-derived
> knowledge, so that retract/suppress permissions act on the same
> applicability lineage that produced the candidate?**

## 2. Гипотезы (проверяются, НЕ истина заранее)

- **H-AA1 (инвариантность):** исключение failure-знаний из S2-пула
  выбора делает выбор инвариантным к failure-derived knowledge:
  каждый S2-кандидат — verified-success член applicability lineage,
  БЕЗ деградации N-траекторий и регрессии.
- **H-AA2 (разблокировка R/S):** при инвариантном выборе simulated
  R/S(verified-success знание) становится наблюдаемым: выбранный
  кандидат = тот же объект, на который направлено право
  (granted → excluded), повторения останавливаются.
- **H-AA3 (граница, ожидание):** адресация сама по себе НЕ
  останавливает stale-петлю: в мире w2 success-кандидат K1
  продолжает выбираться (его aw {E,V1} применим при V1) и повторять
  мёртвый fix-a; петля останавливается ТОЛЬКО R/S-вмешательством
  (или explore-правом, вне AA-1). «Адресация ≠ stale-детекция».

## 3. Механика (факторно; ветки адресации)

Точка правки локализована (strategy.suggest, S2-эксплуатация,
v0.6.x: `pool = exact if exact else rel`; `_match` — aw-проверка для
знаний с полем, legacy-ctx-путь для aw=None). Failure-знания
(aw=None, outcome != success) проходят legacy-матчинг и выигрывают
recency-гонку (свежее success-членов).

- **A0:** v0.6.x как есть (failure-знания в гонке; контроль).
- **A1 (no-failure-action; TRUST1-T2-прецедент):** из S2-пула
  исключаются знания с outcome != "success" (recorder-знания
  «НЕ перевело»); eligible-пуст → S3 (существующая ветка suggest);
  failure-знания остаются в сторе/lineage (append-only), recorder,
  acquisition (L1–L6) не затрагиваются — меняется только выбор
  кандидата.
- **A1b (открытая точка 2):** A1 + «пул = только field-bearing
  verified-success» (legacy-success без aw тоже исключаются).
  В текущем полигоне все success-знания несут aw (E-путь) —
  A1 ≡ A1b фактически; A1b нужен, только если ревью захочет
  проверить legacy-success-класс.

Реализация: ветка-модуль strategy_aa.py = копия strategy.py +
одна правка (фильтр пула в suggest); драйвер импортирует ветку.
Файл слоя strategy.py не изменяется (audit).

## 5. Метрики

- **Инвариантность:** по каждому S2-эпизоду класс выбранного

  менять acquisition); пробы S2 fix-a; L6-walk; r1≡r2; audit.

## 7. Ожидания (expected; сверка, НЕ критерий)

- A1-B: N-истории — траектории ≡ A0 (действия fix-a те же),
  refs-класс всегда success (инвариантность; H-AA1); V2-истории
  (N1V/SV): ≡ A0 (S3 — EF-3 сохраняется); S-истории (SD/SM/NSD/
  E6S): петля через K1 сохраняется (H-AA3: адресация ≠
  stale-детекция).
- A1-R/S@E4: SD/E6S — триггер E4 на 2-м failure; R/S(K1) →
  следующий эпизод: пул пуст (K1 исключён, failure-знания не
  кандидаты) → S3; повторений fix-a после триггера = 0;
  checks granted→excluded = True (H-AA2).
- A0-R/S@E4: повторения = 1 (EP-1-результат, контроль: без
  адресации R/S бессильны).
- A1-R/S на NpD: R(S3-остановка) → восстановление НЕ достижимо
  (K1 исключён навсегда, F не кандидаты; re-learn в эксплуатационном
  цикле отсутствует) — фиксируется как граница R-семантики для
  EP-2 (постоянный retract vs до-подтверждения/связка с re-learn),
  НЕ дефект AA-1.
- E6S: конфликт успехов (K1/K2 оба success): A1-пул = K1,K2 —
  recency K2 (как A0); R/S-объект = последний verified-success
  член = K2.

## 8. Критерии (заранее)

- **PASS-форма AA-1:** (1) A1-инвариантность: failure-refs == 0 на
  всех A1-B-прогонах; (2) регрессия чиста (A0 и A1: S0-эквивалент,
  L6, audit); (3) R/S-механика разблокирована: на A1-R/S@E4 (SD/
  E6S) повторений после триггера == 0 и checks granted→excluded;
  (4) N-траектории A1 ≡ A0 (действия); (5) **AA-1 PASS (адресация
  исправлена) и R/S PASS (permission реально воздействовал на
  правильно адресованный candidate) — два РАЗДЕЛЬНЫХ утверждения
  отчёта** (связаны, но не одно); дополнительно: store append-only;
  acquisition не изменён; никаких новых applicable_when от failure
  (aw всех созданных знаний — только success-путь); r1 ≡ r2.
- **PARTIAL:** инвариантность без разблокировки (или наоборот) —
  границы per-пункт.
- **FAIL:** инвариантность не достигнута или регрессия деградировала.
- «Победители» не назначаются: A1 — кандидат в адресацию
  (интеграция в strategy — отдельный gate по слову профессора);
  A1b — по решению ревью.

## 10. Открытые точки — РЕШЕНИЯ (УТВЕРЖДЕНО профессором 10.09.2026;
## все шесть приняты; уточнения ниже; FREEZE выполнен)

**Утверждено с уточнениями профессора:** (1) фильтр — строго ДО
цикла matching (нельзя позволять failure-knowledge попасть в тот же
selection path, иначе результат назовём свойством AA-1 ошибочно);
(2) A1b не вводим (лемма; возможный контрпример — execution
finding, не повод платить вычислительным налогом заранее);
(3) грид 68 — принято как сокращение, ДОКАЗАННОЕ (терминальные
триггеры N1D/NAD/NSD-R/S@E4: ожидание B проверяется, отдельной
веткой не становится); (4) S3 = stop — состояние AA-1; вопрос
«stop → permission to explore?» переезжает в EP-2 (иначе одним
экспериментом чиним три этажа); (5) E6-объект (K2/K1) — статус
ОБЪЕКТА-КАНДИДАТА, не новая семантика permission; (6) постоянный
R: AA-1 проверяет «правильно ли выбран объект», а не «имеет ли он
право быть retracted»; вопрос значения «retract» для когда-то
verified-success знания в append-only store — EP-2.

1. **Форма ветки → РЕШЕНО: копия-модуль strategy_aa.py.** Основание:
   (а) прецедент — baseline-копии приняты в лаборатории
   (strategy_v05_baseline.py, strategy_v5 для STALE); (б) in-process
   патч suggest невозможен чистой обёрткой — фильтр стоит в середине
   suggest (после сборки пула, до цикла матчинга), обёртка
   потребовала бы дублирования функции целиком; (в) audit strategy.py
   остаётся тривиальным (файл слоя не изменяется; diff копии — одна
   правка, фиксируется в PROTOCOL). Реализация: strategy_aa.py =
   копия strategy.py + ОДНА правка в suggest: фильтр пула
   `pool = [r for r in pool if outcome(r) == "success"]` (outcome из
   context записи) ДО цикла `_match`/eligible; пусто после фильтра →
   S3 (существующая ветка). Все прочие функции (включая _addr_cmd_of)
   — без изменений; драйвер импортирует strategy_aa как strategy.
2. **A1b → РЕШЕНО: отдельной веткой НЕ вводить; фиксируется лемма.**
   Лемма A1≡A1b: в историях AA-1 (learn-фаза всегда с E-контекстом)
   каждый verified-success член линии несёт applicable_when;
   legacy-success (success без aw) не возникает ни на одной клетке
   грида → фильтр «по outcome=success» (A1) ≡ фильтр «по aw»
   (A1b). Если при прогонах возникнет legacy-success — execution
   finding; A1b-ветка — отдельным решением. Экономия: −17 policy-
   прогонов × r1/r2.
3. **Грид → РЕШЕНО: 34 × r1/r2 = 68 (как в §6).** Основание: полный
   грид уже компактен (68 прогонов ≪ EP-1: 100); сокращения
   (NSD-терминальные R/S@E4: −4; A0-B на N1V/SV/NSD — деривация из
   EP-1 B-records: −6) сэкономят ~10 минут, но внесут зависимость
   от внешних records; чистота и самодостаточность дороже. Клетки
   R/S@E4 на NSD помечаются «терминальный триггер (EF-4 EP-1):
   ожидание ≡ B», но прогоняются (данные для полноты). V2-истории
   (N1V/SV) остаются в B-режиме обеих веток (контроль: A1 не ломает
   S3-поведение при V2).
4. **Связка S3→X → РЕШЕНО: в AA-1 НЕ вводится (ни режимом, ни
   контролем).** Основание: EP-1 установил explore = permitted
   verification как ОТДЕЛЬНЫЙ результат; AA-1 отвечает на свой
   вопрос (инвариантность выбора + разблокировка R/S-механики).
   Связка «S3-остановка (адресация) → право проверки (explore)» —
   семантически EP-2-материал (граница прав при корректной
   адресации). S3-поведение A1 измеряется как есть (S3-эпизоды в
   траекториях — метрика §5), без подключения X.
5. **E6S-R/S-объект → РЕШЕНО: последний verified-success член линии
   (= K2 на E6S, = K1 на прочих).** Основание: при A1 пул выбора =
   success-члены {K1, K2}; R/S-объект (последний success) определён
   и уникален (в EP-1 E6-R/S были undefined — пул вёл failure-
   знание; при A1-адресации объект появляется). K2 = знание
   {E:absent}+obs V[1,2] (conflicting success). Ожидания: A0 —
   повторения = 1 (как EP-1); A1 — 0 повторений и excluded-проверка.
6. **R-семантика для EP-2 → РЕШЕНО: в AA-1 — постоянный simulated
   retract/suppress (весь горизонт прогона, как EP-1).** Вариант
   «до-подтверждения» (временный suppress, снимаемый первым
   verified-success членом линии после триггера) — ДРУГОЕ право со
   своей семантикой; фиксируется как открытый вопрос EP-2 (после
   AA-1: если постоянные R/S при A1 останавливают повторения на
   S-историях, но блокируют восстановление на NpD — EP-2 измерит,
   спасает ли временность). В AA-1 не расширяется.
