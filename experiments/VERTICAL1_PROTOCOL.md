# TSARAPINA VERTICAL-1: ПРОТОКОЛ ПЕРВОГО ВЕРТИКАЛЬНОГО ЭКСПЕРИМЕНТА (07.09.2026)

**Статус: ЗАМОРОЖЕН до прогона. Архитектурный карантин: ни одного
нового слоя/механизма; fine-tuning НЕТ; модель неизменна.**

## Главный вопрос (холодная формулировка, профессор)

> Даёт ли внешний замкнутый контур Царапины устойчивое преимущество
> над той же самой Gemma без этого контура при повторяющихся
> задачах, где результат действия можно объективно проверить?

То есть: меняется ли поведение агента вследствие накопленного
внешнего опыта и проверенного знания **при неизменных весах
модели**? Не «стала умнее», не «появилось обучение» — измеримое
поведение.

## Критерий успеха (на доску)

> Успех = наблюдаемое преимущество Gemma+Царапина над голой Gemma,
> возникающее ПОСЛЕ накопления проверенного опыта и сохраняющееся
> при повторении задачи.
> Отрицательный результат валиден: если после нескольких
> контролируемых повторений внешняя память/стратегия/Update не дают
> измеримого преимущества — гипотеза о пользе текущего контура НЕ
> подтверждена.

## Среда (полигон, синтетический; реальный ssh НЕ трогается)

- systemd-юнит-имитатор **tsasvc.service** (Type=simple, свой демон
  в experiments/vertical1/): состояния active/inactive; это
  «диагностируемый сервис» среза, не настоящий sshd;
- драйвер переводит среду в известное состояние ДО задачи
  (systemctl stop/start tsasvc) — контролируемые эпизоды;
- цель задачи: `service:tsasvc.state = active` (goal).

**Политика полигона (единственные правки замороженных слоёв,
задокументированы; НЕ архитектура):**
1. observer/sensors.py: добавлен сенсор service:tsasvc
   (systemctl is-active tsasvc) — расширение наблюдаемости;
2. executor/executor.py ALLOWED_PREFIXES: добавлены
   `systemctl restart tsasvc`, `start`, `stop` — расширение
   разрешённого набора (политика), механика не менялась.
Оба слоя перетестированы после правок (регрессия обязательна).

## Две системы

- **bare (контроль)**: Task → adapter.propose(gemma3:4b) →
  действия → executor → результат. Никакой памяти между эпизодами:
  Knowledge/Experience/Strategy Царапины НЕ участвуют;
- **tsarapina**: Task → observer(факты) → experience → strategy
  (если релевантное знание есть — S2 детерминированно, без LLM;
  иначе S1-диагностика/LLM-запрос) → executor → result →
  evaluation → update → НОВОЕ знание. Gemma та же, модель та же.

Обе используют ОДИН executor и ОДИН evaluation (одинаковая
«рука» и «линейка»); различие — только внешний контур памяти.

## Режимы и серии

- **D0**: первая задача при пустом знании (baseline, обе системы);
- **D1**: повтор задачи ПОСЛЕ того, как Царапина накопила
  проверенное знание (bare повторяет без памяти — ожидается то же
  поведение, что в D0);
- серии: 3 эпизода D0 + 3 эпизода D1 на каждую систему (малый
  прогон, «намеренно маленький»); среда перед каждым эпизодом
  переводится в inactive;
- **model swap**: после накопления Knowledge (конец D1) — тот же
  контур с провайдером qwen2.5:3b, 2 эпизода: ожидается
  использование накопленного знания (S2) независимо от модели.

## Запись эпизода (минимум, профессор) — в протокол эпизода

task_id / эпизод / система (bare|tsarapina) / состояние среды до /
входная задача / модель+версия конфига / предложенное действие /
фактически выполненное действие / state_before / state_after /
evaluation / knowledge ДО решения (snapshot) / knowledge ПОСЛЕ /
итог (success/failure/unknown) / полный provenance (refs).

## Метрики (не только success rate — траектория)

- M1 успех эпизода (goal достигнут по фактам);
- M2 число действий до успеха (траектория: быстрее ли выбор
  проверенной стратегии в D1 у tsarapina?);
- M3 повторные ошибочные действия;
- M4 использование знания: tsarapina D1: suggestion S2 с
  knowledge_ref (против LLM-перебора в D0);
- M5 восстановление после повторной неисправности (D1 == D0
  задача);
- M6 model swap: контур продолжает использовать знание после
  смены модели (S2 без участия LLM).

## Правила честности

- bare НЕ получает историю/знание (промпт без прошлых эпизодов);
- обе системы получают одинаковую задачу при одинаковом состоянии;
- успех определяется evaluation по фактам (goal), не по словам;
- знания Царапины появляются ТОЛЬКО из проверенных последствий
  (update по evaluation), не из промпта;
- прогон и данные не интерпретируются до завершения серий;
- прогон воспроизводим: seeds фиксированы, команды детерминированы.
