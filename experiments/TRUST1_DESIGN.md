# TSARAPINA TRUST-1 / ЗОНА 3: ДИЗАЙН (черновик на заморозку, 06.09.2026)

**Статус: НЕ ЗАМОРОЖЕН. НЕ РЕАЛИЗОВЫВАТЬ до слова профессора.**
Зона 3 Layer C (порядок профессора): ОЦЕНКА — «какому знанию
доверять при конфликте?». R1 (зона 1) заморожен; aggregation (зона
2) PASS, остаётся explicit-инструментом (НЕ встроена в контур).

## Главный вопрос

> Может ли контур разрешать конфликт релевантных знаний так, чтобы
> выбор действия был обоснован проверенными последствиями, а не
> механическим правилом, — БЕЗ введения trust-числа?

## Контекст (что уже есть)

- S3-защита РАБОТАЕТ: при конфликте релевантных знаний контур
  останавливается (не действует вслепую) — подтверждено UA3
  (LONGITUDINAL-1) и D/E (AGGREGATION-1);
- РАЗРЕШЕНИЯ нет: после S3 контур не имеет процедуры; в сценариях
  оператор вручную retract'ил проигравшие стороны (UA5);
- Recency-выбор среди версий одного (симптом, действие): последнее
  проверенное последствие — уже работает механически (kid3 свежее
  kid2);
- НО: противоречивые версии (X,A)success затем (X,A)failure НЕ
  конфликтуют автоматически (declare_conflict — только ручной);
- failure-знание (X,A2,failure) при recency МОЖЕТ быть выбрано S2 и
  предложить A2 (действие, про которое уже проверено, что оно не
  помогло) — в RELEVANCE-1 R2 (no-failure-action) не понадобился,
  потому что такого сценария не было; в зоне 3 он возникает.

## Разведение (что НЕ путать)

- **A. trust-число** (confidence/score/рейтинг) — 🔴 НЕ СТРОИМ:
  FR-0-урок (не прятать неизвестное в число); confidence=None =
  неизвестно остаётся правилом Knowledge;
- **B. механические правила выбора при конфликте** — исследуются
  как ГИПОТЕЗЫ (recency, evidence_count, failure-исключение) и
  проверяются на шумовом контроле;
- **C. разрешение новыми проверенными последствиями** — процедура
  «конфликт → данные/новый эпизод → проверенный исход → операция
  над версиями» — предмет исследования (что именно должно
  происходить с версиями, кто и когда объявляет/снимает конфликт).

## Кандидаты-механики (факторно, детерминированно, без LLM)

- **T1 auto-conflict**: при создании проверенного знания, чей исход
  ПРОТИВОРЕЧИТ последнему проверенному исходу того же
  (симптом, действие) — автоматический declare_conflict
  (точка: update или явный проход, НЕ внутри Knowledge API);
- **T2 no-failure-action (пересмотр R2 в контексте зоны 3)**:
  knowledge «НЕ перевело» не порождает S2-кандидатов: при выборе
  среди релевантных failure-знания исключаются из recency-гонки
  (остаются в знании, конфликты доступны, S3 не ломается);
- **T3 evidence-count**: при нескольких активных успешных знаниях
  (X,Ai) приоритет стороне с большим числом проверенных
  свидетельств (связь с зоной 2: агрегаты несут evidence_count);
- комбинации: T1, T1+T2, T1+T2+T3 — сетка как в RELEVANCE-1.

Гипотеза-граница (заранее): если любое механическое правило
ломается на шумовом контроле (failure по внешней причине при
правильном действии — причинного слоя у контура НЕТ), зона 3
закрывается выводом: **разрешение конфликтов = цикл новых
проверенных последствий, а не вычисление доверия; trust-число не
строится (и не должно строиться)**.

## Сценарии (синтетика, как в AGGREGATION-1; без полигона)

- S1 UA-канон: (a,fix-a,success) → (a,fix-a,failure): ожидание —
  auto-conflict → S3 (не петля); до learn-разрешения контур не
  повторяет fix-a вслепую;
- S2 чередование: (a,fix-a,s),(a,fix-a,f),(a,fix-a,s): recency-выбор
  возвращается к fix-a после третьего эпизода; версии целы;
- S3 конфликт действий: (a,fix-a,s) + (a,fix-b,f) (без declare):
  T2: S2 выбирает fix-a (failure-знание не кандидат); без T2 —
  recency может выбрать fix-b (петля) — измеряется;
- S4 шумовой контроль: (a,fix-a,s), (a,fix-a,f-внешняя-причина),
  (a,fix-a,s): recency спасает; цена = 2 эпизода; T1 не должен
  заблокировать возврат (конфликт снимается/новый success
  перевешивает — какая операция: retract failure? restore?
  НИЧЕГО не удаляется — проверяется поведение выбора);
- S5 evidence: (a,fix-a,s)×3 (агрегат, evidence=3) + (a,fix-b,s)×1:
  T3: выбор fix-a (больше свидетельств); без T3 — recency может
  выбрать fix-b (свежее);
- S6 mixed + устаревание-среда (fix-a2 появляется): полный UA-цикл
  с T1+T2+T3: конфликт → S3 → learn fix-a2 → выбор fix-a2.

Каждый сценарий: baseline (текущая v0.2) vs T-комбинации; метрики
M1–M5.

## Метрики

M1 петли: число эпизодов/действий до корректного поведения в
сценарии (в бесконечной петле — зафиксировать);
M2 корректность выбора: совпадает ли выбранное действие с «истиной»
сценария (fix-a/fix-b/fix-a2 по построению);
M3 история: все версии целы (ничего не удалено; retract/conflict
только по операциям);
M4 S3-защита сохранена (где конфликт реален);
M5 детерминизм (повтор сценария — тот же выбор);
M6 swap-формальность: S2/T-механики без LLM (no-llm-импорты).

## Критерии (заранее)

**PASS**: существует комбинация T, на которой S1–S6 дают: S1 — S3
без петли; S2/S4 — возврат к fix-a после свежего success; S3 — fix-a
(без петли); S5 — fix-a; S6 — fix-a2 после learn; история цела;
детерминизм. + ни одна T-комбинация не ломает регрессию 9/9.
**PARTIAL**: часть сценариев чинится; остальные — граница механики.
**FAIL/граница**: механические правила не проходят шумовой контроль
(S4) → зона закрывается выводом «разрешение = цикл проверки, не
вычисление» (полноценный отрицательный результат).

## Красные ограничения

🔴 trust-число/confidence-вычисление; 🔴 ML/эмбеддинги/LLM-судья;
🔴 удаление версий при «разрешении» (история не трогается);
🔴 изменение Knowledge API/Update/R1 (механики — на уровне
процедур контура/Strategy-v3 ветки, как в RELEVANCE-1);
🔴 «снятие конфликта» как стирание: конфликт остаётся в истории;
🔴 причинный слой (не строим: failure-причины невидимы — это
граница, которую измеряем, а не чиним).
