# TSARAPINA AGGREGATION-1: ДИЗАЙН (зона 2; на заморозку, 06.09.2026)

**Статус: ДИЗАЙН. Код за воротами до фиксации протокола.**

## Главный вопрос

> Можно ли поток повторяющихся, проверенных эпизодов превратить в
> более компактное представление знания, сохранив provenance,
> различимость конфликтов и эквивалентность решений Strategy?

НЕ «умеет ли система объединять записи», а:
> можно ли уменьшить представление без потери свидетельств и
> поведенческой информации?

## 1. Что считать aggregation (разведение)

- **A. Storage deduplication** — физически одинаковые записи хранятся
  один раз: почти тривиальная оптимизация, НЕ исследовательский
  результат (не измеряется как успех);
- **B. Evidence aggregation** — эпизоды остаются отдельными
  свидетельствами, появляется одно агрегированное представление
  `K_agg { experience_refs: [E1..En], evidence_count: n, ... }`;
  E1..En НЕ исчезают;
- **C. Semantic aggregation** — несколько свидетельств → компактное
  правило (symptom → action, support, evidence). НЕ считается
  правильным только потому, что компактнее.

AGGREGATION-1 работает на уровне B (+ проверяет границу C через
decision equivalence), без объявления «семантического обобщения».

## 2. Гипотезы

- **H-A1: компактность без потери свидетельств.** При повторе
  одного проверенного случая aggregation: уменьшает число активных
  Knowledge-представлений; сохраняет ВСЕ исходные experience_refs;
  сохраняет provenance-цепочку до Fact → Raw; сохраняет историю; не
  меняет решение Strategy там, где исходное и агрегированное знание
  эквивалентны.
- **H-A2: конфликт не схлопывается.** E1 → fix-a1 → success и
  E2 → fix-a2 → success (один симптом) НЕ превращаются в
  «symptom → fix-a1/a2», если запись уничтожает различие случаев.
  Минимум: `K_conflict {status: conflicted, evidence: [E1,E2]}` или
  сохранение отдельных конкурирующих знаний.
  Компактность не покупает право забывать конфликт.

## 3. Базовый контроль (C0: no aggregation)

R1 интегрирован и заморожен — Strategy v0.2 ОДИНАКОВА в обоих
вариантах:
```
контроль: episodes → Knowledge 1..N → R1 Strategy
эксперимент: episodes → aggregation → compact Knowledge → R1 Strategy
```
R1 не меняется. Иначе невозможно понять, что дало эффект.

## 4. Материал (маленький диагностический набор, 4 класса)

- **A. Exact duplicates**: A → fix-a ×6 (E1..E6). Ожидание: 6
  свидетельств → 1 агрегат с 6 refs;
- **B. Same action, different episodes**: A → fix-a ×3, эпизоды
  различаются контекстом/обстоятельствами (проверка: агрегация не
  отождествляет грубо);
- **C. Same symptom, different successful actions**: A → fix-a,
  A → fix-b (оба проверены) — вариативность знания, агрегация
  обязана её сохранить;
- **D. Contradictory outcome**: A → fix-a → success; A → fix-a →
  failure — контрольная зона конфликта;
- **E. Success/failure разных actions**: A → fix-a → success;
  A → fix-b → failure — сложный конфликт;
- **F. Mixed A+B+C+D** — поведение в общей куче.

Каждый набор прогоняется: baseline (без агрегации) и aggregation,
затем через ОДНУ И ТУ ЖЕ R1 Strategy.

## 5. Метрики (фиксируются ДО реализации)

- **M1. Compression**: `compression_ratio = active_before /
  active_after`; отдельно хранить `total_evidence_count` (запись с
  20 свидетельствами ≠ запись с 1);
- **M2. Provenance coverage**: все исходные Experience IDs достижимы
  из агрегированного знания (K_agg → E → Fact → Raw):
  `recovered_original_refs / original_refs`; цель 100%;
- **M3. Decision equivalence**: для одинакового состояния до/после:
  same candidate action, same relevance, same strategy. Изменение
  решения без основания = loss;
- **M4. Conflict preservation**: conflict_before == conflict_after,
  обе стороны трассируемы;
- **M5. Determinism**: одинаковый набор свидетельств → одинаковый
  aggregate ID и представление;
- **M6. Swap**: Gemma → qwen2.5:3b после aggregation: компактное
  знание остаётся внешним, Strategy та же, поведение не зависит от
  модели.

## 6. Decision equivalence ≠ semantic correctness (в протокол)

Если агрегация создала плохое правило, но тестовый набор дал
правильный fix-a: decision equivalence = PASS, но semantic
correctness = UNKNOWN. И наоборот. Успешный игрушечный сценарий НЕ
выдаётся за доказательство обобщения.

## 7. Минимальный grid

```
A: 6× одинаковый success        — чистая компрессия
B: 6× same action, разн. эпиз.  — provenance
C: same symptom, разн. actions   — различимость вариантов
D: success + failure (same act.) — конфликт
E: success/failure разн. actions — сложный конфликт
F: mixed A+B+C+D                 — поведение в общей куче
```
Каждый набор: baseline + aggregation → R1 Strategy → сравнение.

## 8. Критерии

**PASS**, если одновременно: (1) активное Knowledge компактнее там,
где есть повтор; (2) provenance coverage = 100%; (3) конфликты
различимы; (4) Strategy сохраняет ожидаемые решения; (5) агрегация
детерминирована; (6) swap сохраняется; (7) старые Experience/Raw не
изменяются и не удаляются.

**PARTIAL**: компрессия работает, provenance сохраняется, но
поведение меняется в некоторых допустимых случаях — граница
представления (ценный результат).

**FAIL**: компактность достигнута за счёт потери provenance или
конфликтов (особенно ценный отрицательный результат).

## 9. Красные ограничения (НЕ делать)

🔴 не вводить trust; 🔴 не вводить ML-кластеризацию; 🔴 не делать
embedding similarity; 🔴 не делать LLM-суммаризацию Knowledge;
🔴 не вводить забывание; 🔴 не менять Update; 🔴 не менять R1;
🔴 не пытаться обобщать «A → fix-a» на новый симптом C.

AGGREGATION-1 отвечает на «можно ли сжать уже проверенное знание»,
а НЕ «можно ли из него вывести новое знание». Это разные вещи.

## Архитектурная граница

```
Experience
   ↓
Knowledge
   ↓
Aggregation
   ↓
compact Knowledge  (evidence_refs, history, conflicts)
   ↓
R1 Strategy
   ↓
Action

Raw/Fact/Experience — свидетельства: не изменяются, не удаляются.
Aggregation меняет ПРЕДСТАВЛЕНИЕ знания, но не свидетельства.
```

Проверяемое утверждение зоны 2 (если эксперимент пройдёт):
> избыточное операциональное знание можно представить компактнее
> без потери его свидетельственной структуры и поведения.
