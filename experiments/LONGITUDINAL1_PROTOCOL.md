## Вопрос

> Становится ли система с внешним замкнутым опытом со временем
> лучше самой себя на повторяющихся и связанных задачах, тогда как
> базовая модель остаётся той же? Появляется ли накопительная
> эффективность (класс задач решается дешевле), перенос на
> связанные ситуации, корректная реакция на устаревание знания?

Рабочая формулировка (не «обучается»):
> «Замкнутый внешний контур позволяет системе приобретать
> проверенное операционное знание и использовать его в
> последующих решениях при неизменных весах LLM».

## Среда (расширение полигона VERTICAL-1; только политика, не слои)

- tsasvc с «болезнями» — флагами-блокировками, демон падает при
  старте, пока хоть один флаг болезни существует:
  - A: /run/tsasvc.lock.a; лечение fix-a (снять lock.a + start);
  - B: /run/tsasvc.lock.b; лечение fix-b;
  - C: /run/tsasvc.lock.c; лечение fix-c (появляется только в
    E41+; никогда не показывается — «новая» ситуация);
  - A+B: оба флага; лечение fix-ab = fix-a + fix-b
    (последовательность двух известных лечений);
- команды fix-* — отдельные скрипты в PATH полигона; LLM их не
  знает и не выводит из текста задачи; в allowlist Executor
  добавляются (политика, задокументированно);
- различитель болезни в задаче/опыте: problem-строка вида
  "tsasvc.service inactive symptom=a" — токен симптома уникален;
  **известное ограничение**: Strategy-матчинг ≥1 общего токена не
  различает классы — это измеряется, а не чинится (карантин);
- наблюдатель: сенсор симптома (ls /run/tsasvc.lock.*) — политика.

## Серии (профессор)

```
E1–E20   накопление истории (обучение/решение класса A, затем B:
         E1 learn-A (оператор), E2–E10 tsar решает A + bare-контроль
         на части; E11 learn-B, E12–E20 tsar решает B)
E21–E30  повторы известных ситуаций (A и B вперемешку; bare —
         каждый раз с нуля)
E31–E40  комбинации известных ситуаций (A+B; E31 learn-AB —
         оператор показывает fix-ab, E32–E40 tsar решает AB)
E41–E50  новые ситуации (C — НИКОГДА не показывалась; перенос?
         bare-контроль на тех же задачах)
```
Хронология мира: внутри серий состояния мира связаны (результат
эпизода n — состояние для n+1: каждый эпизод начинается с
перевода среды в заданную болезнь; «связанность» = знание,
полученное в n, доступно в n+1).

## Устаревание (отдельный сценарий, в конце)

Среда меняется: болезнь A теперь требует fix-a2 (снять lock.a +
lock.extra; fix-a больше не помогает). Последовательность:
K_old(fix-a) → эпизод → failure → новое знание K_fail →
**declare_conflict(K_old, K_fail)** (оператор, по проверенным
последствиям) → поведение Strategy (ожидание: S3 — защита от
слепого повтора; измеряется, не чинится) → оператор показывает
fix-a2 → K_new → оператор retract K_old/K_fail (аудит) → S2:
fix-a2. Метрики: не повторил ли контур устаревшее действие после
declare_conflict (до показа fix-a2); сколько действий/эпизодов
потребовалось до восстановления.

## Гипотезы (открытые исходы, включая дефекты)

- H-L1: накопление: после learn система решает класс через S2
  (1 действие) — ожидается (подтверждено v2);
- H-L2: накопительная эффективность: actions_to_success на повторах
  (E21–30) не растёт и не падает ниже 1; **redundant_actions = 0**
  на знакомых классах;
- H-L3: повторное появление старого класса ПОСЛЕ обучения новому
  (A после B): **открытый исход** — известный риск: S2 выбирает
  самое свежее релевантное знание; если контур применит fix-b к A
  и зациклится на failure-знаниях, это фиксируется как дефект
  выбора знания (граница Strategy; НЕ чинится в этом эксперименте);
- H-L4: комбинация AB после learn-A и learn-B: открытый исход
  (ожидание: без learn-AB контур не соберёт последовательность —
  проверяется перенос; learn-AB даёт S2);
- H-L5: новые ситуации C: открытый исход (ожидание: контур и bare
  оба не знают fix-c; если переноса нет — граница «приобретение
  ≠ обобщение»);
- H-L6: устаревание: после declare_conflict контур НЕ повторяет
  устаревшее действие вслепую (S3-защита) — проверка.
- H-L7: knowledge-рост: число записей и «мусор» (повторные
  failure-знания одного класса) — измеряется: разрастание
  Knowledge без пользы = отрицательный сигнал для агрегации
  (RESEARCHABLE).

## Метрики (на эпизод и по сериям)

M1 success/failure; M2 actions_to_success; M3 redundant_actions
(действия после успеха/повторные бесполезные до успеха);
M4 episode efficiency ОТНОСИТЕЛЬНО собственной истории: для класса
X: actions(En) vs минимум по прошлым X-эпизодам (становится ли
дешевле); M5 knowledge: доступное до/после, использованное
(knowledge_refs), рост числа записей; M6 bare-контроль на тех же
задачах (одинаковая «рука»/«линейка»); M7 swap-контроль (gemma →
qwen2.5:3b, конец серий, 2 эпизода класса A) — знание работает
независимо от модели; M8 устаревание: эпизоды до восстановления.

## Контрольные условия (профессор)

- training/history (E1–E40, кроме bare-контролей) отделены от
  held-out (E41–E50: C не показывалась никогда);
- bare не получает историю/знание; одинаковые задачи/состояния;
- успех — только evaluation по фактам (goal);

- каждый успешный/неуспешный эпизод tsar создаёт новое знание
