# K0 — АКТ v33-A: F1-feedback при повторной попытке (строгая грамматика; ветка A)

Дата: 2026-10-17 · Подготовил: DeepSeek TUI · Для постановщика K0 и внешней проверки
Статус: **v33-A подготовлен; проверки пройдены; публикуется ДО запуска.
Запуск НЕ ВЫПОЛНЕН и будет выполнен только по отдельному решению после ревью
(без автоперезапусков).** v26–v32 и их артефакты — заморожены.

## 1. Основание

Решение постановщика от 2026-10-17: выбран **вариант A** — «строгая грамматика F1 +
явная обратная связь при повторной попытке»; «ветку B пока не развиваем»;
«реализацию можно готовить, но это решение не является разрешением на запуск
модели». Критерий §6 проекта подтверждён; две оговорки учтены:

- формулировка о частоте `?` исправлена: независимой выборки для оценки нет
  (одно аномальное наблюдение + детерминированные повторы); «1 из 12» как
  вероятность не трактуется (правка в `K0_V32_F1_ANOMALY_FACTS.md` §7);
- идентичность клиентского запроса исключает различия в сборке запроса на нашей
  стороне, но не доказывает причину в Ollama; точная причина не установлена
  (правка в §5 фактов и в `K0_V33_DESIGN_DRAFT.md` §2).

## 2. Изменение (одно — механизм обратной связи F1)

**`prompts.py`**: блок `[ОТКАЗ F1]` добавляется в F1-промпт **начиная со 2-й
попытки** и только при наличии причины:

    [ОТКАЗ F1] предыдущий ответ невалиден:
    - <problems: «строка N: невалидный PREDICT» / «пропуск клетки …» / …>
    - <сырые строки, привязанные к problems>
    Допустимы только значения present или disappeared; повтори ровно 9 строк
    формата PREDICT: <объект> T=<t> H=<h> = <present|disappeared>; другие строки
    недопустимы.

`build_f1(ctx, attempt=1)`; диспетчер `build_prompt` передаёт `attempt` в F1-билдер.
Грамматика, критерии §9, мир, батарея, параметры модели — **без изменений**;
`?` допустимым значением **не становится**; число попыток — по-прежнему ≤3, после
3 невалидных — штатный `invalid_final F1`.

**Служебные приведения (полный список):**

- `parser.py` — `ForecastResult.bad_raw` (сырые строки, привязанные к problems;
  для перечня невалидных строк в блоке отказа);
- `session.py` — `AgentContext.f1_rejection`; сохранение причины отказа F1 после
  каждой невалидной попытки, сброс после успешной; передача причины в контекст
  попытки ≥2; докстринг; метки v33;
- `calls.py` — `render_context` пишет `f1_rejection` для F1 (видимость входа
  в JSON-артефакте вызова);
- `run_first.py` — `RUN_NAME` → `run_K0-M3_101_v33`;
- тесты: `test_channel.py`/`test_session.py` — ожидания v33; новый
  `tests/test_f1_feedback.py` (T1–T4: блок на попытке 2 с перечнем строк; отсутствие
  блока без отказа; 3 невалидных → `invalid_final F1`; видимость причины в
  артефакте); предохранитель v30 (R1–R4) — без изменений;
- `admission_checks.py` — добавлены V33/V33-P/V33-S; V32-P/V32-S переведены на
  **замороженные** пары v31↔v32; A20 → v33;
- протокол `K0_PROTOCOL_v33.md` — копия v32, отличается ровно строкой реестра §13;
- фрозен-копии: `K0_PROMPTS_v32.py`, `K0_SESSION_v32.py`, `K0_CALLS_v32.py`.

**Служебное замечание (найдено до публикации):** при первом прогоне подготовки
фрозен-копии v32 были сняты уже после правок (диффы пусты). Проверка допуска
поймала это до публикации; копии восстановлены обратным применением правок и
сверены по sha256 с актом v32 §7 (`ad40ccc9…`, `4f6601da…`, `563aa726…`); диффы
перегенерированы. Критериев это не меняет.

## 4. Допуск (офлайн; на v33-комплекте)

- Офлайн-сюита: **260/260 OK** (256 прежних + 4 новых; строгий режим
  `-W error::ResourceWarning`).
- Проверки допуска: **PASS=50 / FAIL=0 / OPEN=1 / NOTE=1**. OPEN — A20b (живые
  байты канала; закрывается канарейкой прогона).
- T1: причина отказа с перечнем строк (включая `- строка 4: PREDICT: O3 T=2 H=2 = ?`
  и `пропуск клетки …`); T2: без отказа блока нет; T3: 3 невалидных → стоп;
  T4: `f1_rejection` виден в JSON-артефакте. R1–R4 без изменений.
- Укладка: блок отказа (~200–400 Б) добавляется только в повторы F1; лимит §12
  не менялся.

## 5. Конфигурация при запуске (после отдельного разрешения)

- Каталог `runs/run_K0-M3_101_v33/`; паспорт: `series`/`mode` = `K0-M3`,
  `protocol_version` = `v33`.
- Модель и параметры — без изменений: `gemma4-e4b-heretic:q4km`, loopback
  `127.0.0.1:11434/api/chat`, `temperature=0`, `seed=1729`, `think=false`,
  `num_predict=256`, `num_ctx=4096`, `keep_alive=30m`.
- Лимиты/стопы без изменений: 30 вызовов / 45 мин / 100k токенов / промпт ≤4000;
  STOP; классы O1; `invalid_final`; `invalid_f2`; предохранитель `response_loop`
  (v30, ред.2); канарейка — первым шагом.
- Критерий прогона (зафиксирован заранее, §6 проекта): цель M3 — проба именно
  в клетке зарегистрированной H1; повторная регистрация и другие клетки успехом
  не засчитываются; номер принятой попытки F1 фиксируется в отчёте; отчёт — шесть
  пунктов v32 + номер попытки.

- v26–v32 и артефакты их прогонов — заморожены; правок по ходу не будет; при
  остановке — фиксация. Другие seed и повторные запуски — только отдельным решением.
